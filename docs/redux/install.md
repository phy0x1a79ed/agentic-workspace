# Install and bootstrap

## Purpose & Contents

This doc holds how awm reaches a node and how awm is built: the language of the core, the build, the plugins, and the environments that test a fresh install. Thread 1h produces it.

Which node holds which role belongs in `fleet.md`. How a deploy moves through the branches belongs in `routines.md`.

## Requirements

- **R115.** A plugin is a project of its own, and awm installs it straight from its git repository. Installing one needs no code in awm, such as a line that registers a service or a page. The plugin carries everything awm needs to load it. Tony: "by true plugins, I meant that the current system is not rigorous.", "each plugin should be its own project" and "plugins should be installable from a git repo directly and not require any additional code in awm itself, like registering services or pages." (2026-11-02).
  1. A page is a plugin too. Tony: "pages id argue are also plugins."
  2. One plugin may hold several services and pages. Tony: "a plugin can have a combination and multiple services and pages".
  3. A plugin has a version pin and its own refresh hook (`routines.md` R33). It runs on the host (R116 item 4) and owns its runtime. awm runs no package manager for a plugin. Tony: "awm shouldnt be responsible for any package managers like mamba. if a plugin uses it, how can we put that into the contract?" (2026-11-06).
     - A core plugin is written in Rust and ships as one static musl binary. mizar's container builds it (R113), and awm pins it the way it pins the core binary. A change to one core plugin ships only that plugin's binary. Tony: "for the awm core plugins that come with a typical install, if the gateway is in rust but the core plugins are python, then that defeats the purpose." (2026-11-06).
     - Any other plugin may be written in any language. Its own install hook builds its runtime, with any package manager it chooses. The gateway runs the hook only when that plugin's install stamp changes. Tony: "we can allow python, or really anything for plugins" (2026-11-06).
  4. The core plugins stay in the awm repository, each in its own folder. A plugin is a folder whose top level holds one manifest file that fills out the plugin contract. awm installs it from a git repository or from a folder alike. Tony: "we can also keep core plugins in awm repo itself. then installable is from a folder structure, maybe some file at top level that fills out contract" (2026-11-02).

The `channel` plugin carries the tether (`channels.md` R110). The journal carries precedence (`fleet.md` R107 item 9). Tony: "the browser VPN, dev, transcripts, DSH, and social, I'd argue, are also core plugins." "Tether and mic should also be core." and "let's keep KB as a core service." (2026-11-03). Tony: "not core: 2fa, trillium, ssh, vpn" (2026-11-06).
     - One plugin serves one concern. kb serves the `journal`, `search` and `transcripts` tools. routine absorbs events. channel absorbs relay, and the relay service runs only on the public host. auth absorbs httpsfront and the `tlsfront` library: it serves the TLS front and the passkey login, so no other plugin runs a TLS front of its own. The gateway holds no TLS and no login. Tony: "since we are porting, we can also take this time to consolidate the code base to make it more coherent" and "id like to keep the gateway pure, you can consolidate these, it just has to stay a plugin. gateway is pure logistics." (2026-11-06).
     - kb is the model of a search source. A new source is a plugin that declares `[[service.archive]]` in mode `index` or `live`, and search needs no change (`fleet.md` R136).
     - Every other plugin is not core: 2fa, trilium, ssh, vpn, wake, engcyc, rlm-factorio, zotero and claude-science. Each is a project of its own, so it updates without touching the core (`routines.md` R33).
     - The Trilium server is our fork, `projects/trilium`, a project of its own. Each fork release publishes an installable tarball. The `trilium` plugin installs the tarball of the release that it pins, and never builds the fork. A fork change reaches the live services by one route: release the fork, bump the pin, and deploy (`fleet.md` R105). Tony: "trillium is a fork so it cant be core" and "accept if: we publish installable tarball distributions  from our fork that is used by awm changes from the local trillium project (our fork) gets a straightforward deploy route to update live services" (2026-11-03).
       - A change made as a note, such as the board page, a widget, a script or a theme, needs no build. It goes live through the `trilium` tool. A change to the fork's code runs first on the fork's dev server on mizar, against a copy of a vault snapshot, never against the live vault. Only a fork release builds a tarball. The fork lives on mizar. Tony: "is there a hot path for trying out changes to trillium without going through a full build?" and "agree. migrate trillium to mizar" (2026-11-03).
     - The one install contract matters more than where a plugin's code lives. Every plugin, core or optional, loads only through its manifest, from a folder or a git repo alike. Moving the optional plugins into projects of their own comes second. Tony: "it's not so much that they move into their own project that is important, though we still want to do this for the optional services. It's more so that we have a standardized install contract so that we can have services be installable from a folder or Git repo." (2026-11-03).
- **R116.** Guards keep a plugin from reaching past its own parts. Tony: "your proposals are good" (2026-11-02).
  1. The manifest lists the plugin's services and pages and what they need, such as secrets, network and other tools. The gateway gives a plugin only what its manifest lists.
  2. Each install pins a commit and takes Tony's passkey (`queue.md` R64), and so does each move to a new commit. One passkey approves every plugin commit of one change together. Tony: "approved commits are fine if we can batch approve for a full change" (2026-11-02).
  3. A plugin may call any tool, whether its manifest names it or not (R117 item 8). The gateway knows a service's call by the service's token, and a page's call by the path of the page that sent it. Trust rests on the tool tiers, the grants and that caller stamp. The review at install (item 4) catches a plugin's intent. Tony: "plugins can call other plugins that are not marked as its dependencies" (2026-11-06). This replaces the per-verb call guard of 2026-11-04.
  4. Installing a plugin trusts it. Tony reviews the plugin at the approval of item 2. Every plugin runs on the host, and its pages share the gateway's origin. A plugin written outside the fleet gets the same review. This replaces a page origin per plugin and a container for a third-party plugin. Tony: "If we just do installing is trusting and analyze the plugin beforehand, is that a problem? Plus, all of the plugins are handwritten by us." (2026-11-04).
  5. A namespace records which plugin owns a name. It never appears in a call: a tool keeps its flat name, such as `journal`. The manifest claims the tool names the plugin serves, and the gateway keeps one table from each name to its owner. An install that claims a taken name is refused. The clash is settled by renaming the tool in one plugin's manifest (R117 item 2). The reserved names gate trust and belong only to core plugins: `awm`, `auth`, `operations` and `journal`. `operations` carries the approver. Page origins, secret grants and the audit log use the owner's name. Tony: "we dont want namespace = tools and we dont want to have to do \"awm namespace/tool\"" and "this works" (2026-11-02).
- **R117.** A plugin depends on tools of other plugins, never on their code. Tony: "ok, but the install contract needs to name where these tools come from. the tool name is changeable in the contract so is not a good source of truth" (2026-11-02).
  1. A plugin calls another plugin only through the gateway, as an agent does. No plugin imports another plugin's code.
  2. Each tool's name is unique across the fleet and is the tool's permanent id. The plugin's manifest declares it, so a fork renames its tools by editing its own manifest. The install config renames nothing. A dependent names each tool it depends on and the major version it needs. Tony: "I'm thinking that names should just be unique" and "We can make the name declared in a file so that forks can rename" (2026-11-03). This replaces the permanent tool UUID of 2026-11-02.
  3. The gateway keeps one live table from each tool name to the plugin that owns it, on this node and its peers. A call looks its name up at call time, so an install, update or removal takes effect at the next call (R144). A node tells its peers when its table changes. An install that claims a taken name is refused and names the owner. A missing name or major refuses the install and names the tool.
  4. Several plugins may serve one interface. The interface has a unique contract name with a major version, such as `harness@1`. Each provider keeps its own tool name and names the contracts it implements. A dependent that needs the contract reaches every provider through it and never names a provider. cch and dsh both implement the harness contract, and reflection needs only that contract (R135). Tony: "Option a. Reflection caller doesnt care about details" (2026-11-03).
  5. A breaking change to a tool raises its major version. The provider and the plugins that call it update in one batch-approved change (R116 item 2).
  6. Shared code is a library, never a plugin. The core plugins live in awm, so they share library crates in the core cargo workspace. Another plugin pins its libraries in its own runtime. A plugin never imports another plugin's own crate or package. Tony: "right, since these are all core and live in awm, there can be shared code" (2026-11-06).
  7. Plugins start together, in no order. A call to a tool that is not up yet waits briefly, then fails with a clear error.
  8. A need is a hard dependency. A plugin declares a `[[needs.tool]]` or `[[needs.contract]]` only for a tool it cannot do its job without, and the loader refuses the plugin while that tool is absent. A need has no optional form. A call to a tool that the plugin does not need passes the gateway as any call does. A call to a tool that no plugin serves fails at once with a `not installed` error that names the tool. A core plugin needs no plugin outside the core. Tony: "dependencies are not used correctly. dependency is a must." and "plugins can call other plugins that are not marked as its dependencies" (2026-11-06).
- **R144.** A plugin change runs hot. Installing, updating, renaming or removing a plugin takes effect without a gateway restart. Only the changed plugin's own services restart (`routines.md` R33). Tony: "Now, plugin changes should run hot without gateway restarts." (2026-11-03).
- **R118.** One test takes a bare container through a fresh install, then adds it to a fake fleet as a new node. The fake fleet is containers too: a throwaway certificate authority, a fake peer, and stubs for `2fa` and `social`. It touches no real login and no real node. The test runs locally on mizar under rootless Docker, and the same script runs in a Claude cloud agent from the GitHub remote (R114). Its Claude login is the access-token-only copy of `fleet.md` R109. Tony: "we should also consider settup up a system that can spawn throway temp environments that act the same" (2026-10-30).
  1. The test runs only when someone asks for it. It is never part of the fast smoke test in continuous integration. Tony: "only when asked. this cant be part of the fast smoke under continuous integration" (2026-11-02).
  2. The cloud agent is the first home of the test. mizar is the fallback when containers fail inside the cloud sandbox. A cloud session costs plan usage only, with no charge for the machine. Tony: "cloud first and same for metasmith." (2026-11-02).
  3. The bootstrap must be fast, so a test run spends its time on the test, not on installing. Tony: "we need to streamline the bootstrap so we dont spend all the time installing" (2026-11-02).
     - A test run installs built artifacts and builds nothing. The core is one static binary from a release on the GitHub remote, built in mizar's container (R113). Each plugin and each part of the fake fleet is a pre-built image (R119). A heavy dependency, such as torch, lives only in the plugin that needs it.
     - The cloud environment's setup script pins the exact version of each artifact and pulls it. The cloud keeps a filesystem snapshot after setup, pulled images included, and reuses it for about seven days. A release changes the pins, so the script changes and the snapshot rebuilds. Setup must finish in about five minutes, or the cloud keeps no snapshot.

Tony: "Pages need a visit count instead of a call count" and "Need to update usage metrics" (2026-11-03).
